# HyperForge

The shared foundry behind SkunkWerkx's Hyper* projects ([HyperUuid](https://github.com/SkunkWerkx/HyperUuid), [HyperCast](https://github.com/SkunkWerkx/HyperCast), and the ingestion round's [HyperTabular](https://github.com/SkunkWerkx/HyperTabular), which reads delimited text and workbooks alike): reusable CI pipelines, 5 real-hardware platforms plus the two musl RIDs and a cross-built Intel macOS, that prove one Rust core against every language binding's real test suite, scaffolding conventions for new bindings, and the build archaeology — learned once, banked here, never re-learned.

## The pipeline

[`hyper-build-native.yml`](.github/workflows/hyper-build-native.yml) is the canonical build: the Rust core compiled fresh on 5 real-hardware legs (linux and windows on x64 and arm64, macOS on arm64), then every binding's actual test suite run against that leg's freshly-built native library — proving the real FFI load/marshalling path per OS, which `cargo test` alone cannot exercise. Ruby's suite runs twice per leg: once forced onto its zero-compile Fiddle fallback, once on the Magnus extension, built and staged on every leg — both Windows legs included, via the `gnullvm` targets. Python has no fallback: the PyO3 extension is built and tested per leg.

A second job in the same workflow, `build-native-musl`, covers `linux-musl-x64` and `linux-musl-arm64`. It builds the core inside a real Alpine container through the [`musl-native`](.github/actions/musl-native) action (whose `build-musl.sh` runs unchanged on a developer's machine with Docker), runs the crate's own suite there, uploads and attests the library as `native-{rid}` like the matrix legs, and runs the bindings that have a musl story against it on Alpine — Ruby's Magnus extension included, built once per Ruby ABI inside that Ruby's own `ruby:*-alpine` image through the [`ruby-magnus-musl`](.github/actions/ruby-magnus-musl) action and uploaded as `ruby-native-{rid}-{abi}` for the caller's musl platform gems. It is a separate job rather than two more matrix rows because the five-leg job installs every toolchain with `setup-*` actions, and most of those do not target Alpine.

A third job, `build-native-osx-x64`, is what is left of the Intel macOS leg. It cross-compiles the core for `x86_64-apple-darwin` on the Apple silicon runner, runs the crate's own suite on it under Rosetta 2, and uploads and attests the library as `native-osx-x64`, so every package still carries it. No binding's suite runs on Intel macOS, and no Magnus or ext-php-rs extension is built for it: Ruby there installs the universal gem and runs on Fiddle over this library.

Two more jobs, `build-static-libs` and `test-swift-static`, cover the three bindings that link the core instead of loading it: Swift on every RID and WebAssembly, Go under cgo on Linux, macOS and Windows (and, with `apple_mobile`, iOS and Mac Catalyst) and under TinyGo on WebAssembly, and a C# Native AOT publish on every RID. The first builds nine no_std static libraries through the [`static-libs`](.github/actions/static-libs) action — every target, macOS and Windows included, cross-compiled on one runner, since a static library is never linked — and uploads and attests them as `static-libs`, laid out by repository path. A caller's `stage-native-binaries.yml` commits the Swift and Go ones (`swift/{Project}Core.artifactbundle`, `go/staticlib`), and `hyper-pack-nuget.yml` packs the C# ones. The second downloads that artifact on each architecture and runs the Swift binding against it through the [`swift-static-suite`](.github/actions/swift-static-suite) action, in Swift's own containers: a glibc consumer, the static Linux SDK and the WebAssembly SDK on the current Swift — the WebAssembly smoke executable also in headless Chrome through a pinned WASI shim — then glibc, musl and WebAssembly again on the declared floor. On macOS and Windows the matrix legs' own archives go straight into the Swift bundle, so `swift test` there links this commit's core too. Go and C# are tested where their toolchains already are: every leg of the matrix job and of the musl job builds its own target's archive first and links it in its own suite. All three scripts run unchanged on a developer's machine. A caller that sets `apple_mobile` gets four more archives from the same job (iOS, the iOS simulator on Apple silicon, and Mac Catalyst on both architectures): the C# ones under `csharp/{Project}/staticlibs/` by .NET RID, Go's under `go/staticlib/`, and Swift's three arm64 ones as `swift/{Project}CoreApple.xcframework`, written whole, Info.plist and headers included, because `xcodebuild -create-xcframework` only exists on a Mac. Linking and running them takes Xcode, a simulator and the .NET workloads, which no leg here carries, so that is the caller's own job.

The shape of a Hyper* repo's CI file (HyperCast's, minus its comments):

```yaml
name: CI — build native, build wasm, test every binding
on:
  pull_request:
  workflow_dispatch:
  schedule:
    - cron: "0 6 * * 1"     # the whole release-mode board, weekly
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
jobs:
  build-native:
    uses: SkunkWerkx/.github/.github/workflows/hyper-build-native.yml@master
    permissions:            # attestation signs with OIDC; a reusable workflow
      contents: read        # can never escalate beyond its caller's grant
      id-token: write
      attestations: write
    with:
      mode: ${{ github.event_name == 'pull_request' && 'pr' || 'release' }}
      project: HyperCast
      crate: hypercast
      pure_env: HYPERCAST_PURE
      csharp_test_project: csharp/HyperCast.Tests/HyperCast.Tests.csproj
      csharp_aot_project: csharp/HyperCast.AotSmokeTest/HyperCast.AotSmokeTest.csproj
      dotnet_version: "11.0.x"
      dotnet_quality: "preview"
      csharp_runtimes_dir: csharp/HyperCast/runtimes
      java_resources_dir: java/src/main/resources/native
      ruby_compat_version: "3.4"
  build-wasm:
    uses: SkunkWerkx/.github/.github/workflows/hyper-build-wasm.yml@master
    with:
      mode: ${{ github.event_name == 'pull_request' && 'pr' || 'release' }}
      crate: hypercast
  build-wheels:
    uses: SkunkWerkx/.github/.github/workflows/hyper-build-wheels.yml@master
    permissions:
      contents: read
      id-token: write
      attestations: write
    with:
      mode: ${{ github.event_name == 'pull_request' && 'pr' || 'release' }}
      crate: hypercast
```

A pull request runs the forge in `pr` mode: every leg, every binding's suite and every floor still run, so the corpus is proven in all eight languages on every platform, but nothing a release alone needs is built or signed — no attestations, no second Ruby ABI, no osx-x64 cross-build, none of the eight native wheels (the Pyodide one still builds and runs its suite in the browser), no ext-php-rs extension (shipped by no package), no ruby.wasm (an interpreter build per Ruby minor, 7–10 minutes each), and no Apple-mobile job in the caller. Those ran on the PR critical path for packaging nobody would ship until the next release; on HyperCast run 37559419462 the Apple-mobile job alone held a board whose slowest leg finished at minute 16 open until minute 44. Every other event — the release's dispatched run and the weekly schedule — runs `release` mode, so the whole board is still exercised between releases rather than first on release day.

No `push` trigger, deliberately: the stage-native-binaries and prepare-release workflows direct-push mechanical commits, and a matrix run on each of those is wasted compute. The one push that does need a run is a release's version bump, and `prepare-release.yml` dispatches it explicitly (see "A library that reports its version" in the ledger).

Two more reusable workflows run in CI beside it: [`hyper-build-wasm.yml`](.github/workflows/hyper-build-wasm.yml) builds the `wasm32` staticlib once for the NuGet package's browser-wasm asset and, given `blazor_check`, `rust_browser_test` and `go_tinygo_smoke`, runs the C# binding's Blazor smoke app, the crate's own wasm-bindgen tests and the Go binding's smoke program — compiled by TinyGo for the browser with the core's `wasm32-wasip1` archive linked in — in headless Chrome; given `ruby_wasm_smoke` and in `release` mode, it also builds the Ruby binding's Magnus extension for `wasm32-wasip1` once per Ruby minor, attests and uploads each archive for the `{crate}-wasm` gem, and runs that gem linked into a ruby.wasm interpreter under Node and in headless Chrome; and [`hyper-build-wheels.yml`](.github/workflows/hyper-build-wheels.yml) builds the nine PyPI wheels — eight native, plus the Pyodide one (`pyemscripten`, for Python in the browser), whose whole pytest suite runs inside Pyodide under Node and in headless Chrome through the [`pyodide-suite`](.github/actions/pyodide-suite) action — installs each on its own platform, calls into it, and attests and uploads it for the release to publish unchanged (see "Build the package where a failure is cheap" in the ledger). The rest are the release side, called from each repo's `release.yml` at tag time: [`hyper-pack-nuget.yml`](.github/workflows/hyper-pack-nuget.yml) packs and attests the `.nupkg` but never pushes it (nuget.org's Trusted Publishing validates the OIDC token against wherever the *executing* workflow file lives, so the push must stay in the caller); [`hyper-publish-crate.yml`](.github/workflows/hyper-publish-crate.yml) and [`hyper-publish-maven.yml`](.github/workflows/hyper-publish-maven.yml) package, attest, and publish the crate and the jar. Gems are packed in the caller directly. Either project's `release.yml` is the working example.

Every input, with defaults, is documented in the workflow file itself. The load-bearing ones: `project`/`crate` (PascalCase and lowercase names everything derives from), `pure_env` (the force-the-fallback env var), `csharp_aot_project` (turns the AOT claim into a per-platform receipt), and the per-binding toggles. Every binding has one (`csharp`, `java`, `swift`, `php`, `ruby`, `go`, `pyo3`, `magnus`), all on by default; a new core joins the pipeline with the bindings it has and turns each of the rest on in the PR that adds it, so its native libraries are built, attested and staged on every platform from the first binding rather than from the last.

## The conventions

The pipeline works across repos because the repos agree on layout — this agreement is the actual shared asset, and new Hyper* repos should adopt it wholesale:

- **One Rust core** at `rust/` (an `rlib` in the manifest, the shared library built from it by the crate's own `cargo cdylib` alias, without Rust's standard library — [The Rust core](#the-rust-core) has the whole recipe and why; zero runtime deps), C-ABI exports, caller-owned out-buffers, no allocator exports. A counting-`#[global_allocator]` test proves any allocation-free claim; a shared conformance corpus (`corpus/*.json`) is replayed by the core and every binding.
- **Native library staging**: `native/{rid}/{lib}` (or the platform's own convention: NuGet `runtimes/{rid}/native/`, Swift `{Project}Core.artifactbundle/{triple}/` for the static libraries it links on every platform, `{crate}.lib` for the Windows triples), with a dev-loop fallback probing `rust/target/release/` so local tests need no packaging step.
- **RIDs**: `linux-x64`, `linux-arm64`, `linux-musl-x64`, `linux-musl-arm64`, `osx-x64`, `osx-arm64`, `win-x64`, `win-arm64` — .NET's names, used by every binding. A binding that cannot ask its runtime which libc it is on (Java, Go, PHP) decides musl by whether the running process has a musl loader mapped (`/proc/self/maps` names `ld-musl-` or `libc.musl-`), not by what happens to be installed on the box.
- **Floors track upstream support.** A language runtime that has reached end of life is not a supported floor, in any Hyper* repo, and the floors match across repos: raise them together when a version ages out.
- **A load probe in every binding**: the core exports `{crate}_version()` (packed `major << 16 | minor << 8 | patch`), and each binding fronts it with an availability check that never throws plus the loaded core's version as text, so a consumer with a fallback gates on the probe instead of catching a load failure around its first real call.
- **Native extensions** for the interpreted tier, where the FFI mechanism itself was the cost. Python is PyO3 only: the extension lives in the core crate behind a `python` feature, maturin builds one `abi3` wheel per platform (Pyodide's included, so Python in the browser runs the same extension), and the `ctypes` fallback is retired in both projects. Ruby is dual-backend: the Magnus extension (`{crate}_native`, behind a `ruby` feature) on load replaces the Fiddle fallback's low-level functions **in place** — everything above them stays shared byte-for-byte — and ships as precompiled platform gems on all eight RIDs, fat across supported Ruby minors and carrying no Fiddle library, with Fiddle as the last resort in the universal gem: an unsupported Ruby, or a platform with no platform gem. `{PURE_ENV}=1` forces the fallback; a `BACKEND` constant reports which is live; a cross-backend agreement test compares deterministic outputs across a subprocess boundary.
- **The core crate** carries a `rust/.cargo/config.toml` declaring `-undefined dynamic_lookup` for the extension builds on Darwin (see the ledger below), and the build aliases the forge and every dev loop run — `cargo cdylib` above all, which the forge calls rather than spelling out a build of its own.
- **Verdicts over exceptions** (parsing repos): every parse returns a discriminated union — the platform's native one (Rust `Result` + closed enum, C# `[Union]` with CS8509-as-error, Swift `enum`, Java sealed interface, Python `match`, Ruby `Data` + `case/in`, PHP `Success|Fault`) — never a thrown exception for bad data. Exceptions are reserved for caller bugs.

## The Rust core

How a Hyper* core is built, and why each piece is the way it is. HyperCast and HyperUuid arrived here by retrofit, one red run at a time (the ledger has the receipts); a new core should start with all of it, because every item is cheaper on day one than after the first release. It is written for someone who knows the languages the bindings are in better than Rust, so the Rust terms are explained where they first matter.

### The hypothesis

A Hyper* core is a small amount of parsing or generation code behind a C ABI, called from eight other languages. Almost none of what makes a Rust shared library large is that code. The rest is Rust's **standard library** (`std`): the panic runtime that prints a message and a backtrace when a Rust program crashes, the unwinder that walks the stack to do it, a DWARF debug-info parser and symbol demangler to make the backtrace readable, and a heap allocator. A core exports plain functions over caller-owned buffers, never allocates, and is proved unable to panic, so none of that is reachable from anything a host can call — and yet it was most of every library we shipped.

So: build the shipped library without `std`, against `core` alone (the part of Rust's library that needs no operating system), and keep everything else about the code the same. Measured, on the libraries the forge stages:

| Library | Platform | With `std` | Without | |
| --- | --- | ---: | ---: | ---: |
| HyperCast | linux-x64 | 436,192 | 109,736 | −75% |
| HyperCast | osx-arm64 | 455,952 | 136,624 | −70% |
| HyperCast | win-x64 | 197,632 | 105,472 | −47% |
| HyperUuid | linux-x64 | 346,528 | 19,048 | −95% |
| HyperUuid | win-x64 | 18,944 | 17,920 | −5% |

Same exports, same code — nothing on a call path changed, only code no call could reach was removed. The libraries now depend on the C library alone (`libc.so.6`, musl's libc, or `KERNEL32`, `VCRUNTIME140` and the universal CRT on Windows), which also retires the musl `libgcc_s` problem in the ledger for the shared library.

**Why the savings differ so much by platform and crate.** On most linkers, link-time optimization already discards `std`'s panic runtime when nothing can reach it — which is why HyperUuid, whose exports cannot panic, was already 18–74 KB everywhere but linux-x64. Two things defeated that:

- **Code that really can panic.** HyperCast's float doors then parsed with `core`'s own float parser, which keeps bounds checks the optimizer cannot remove. Reachable means kept, so HyperCast carried the whole runtime on every platform. (They have their own conversion now, and are in the proof: the ledger has "A float parser the proof accepts".)
- **rust-lld on linux-x64.** Since Rust 1.90, `x86_64-unknown-linux-gnu` links with rust-lld by default (every other Linux target still uses the system linker). lld treats the unwind tables' reference to `std`'s personality routine (the function the unwinder calls in each frame) as live, and that routine can itself panic, which pulls in the panic hook and the backtrace symbolizer behind it: about 315 KB. The same HyperUuid code was 30,080 bytes with GNU ld and 346,840 with lld; `-Wl,--why-live=` prints the chain. Without `std` there is no such personality routine to keep.

**What would not have worked.** Making HyperCast's two float doors panic-free first, so the runtime could be optimized away, was the obvious idea. Measured with float parsing stubbed out entirely, the `std` library was still 414 KB on linux-x64, for the lld reason above. Dropping `std` is what does it. The float doors were made panic-free later, for the proof and not for the size: it cost 1.7 KB.

### The recipe

Items 1–10 are in both HyperCast and HyperUuid, item 11 in HyperCast only (HyperUuid has no `rustfmt.toml`), and item 12 in HyperUuid only; copy them from there rather than from this description.

1. **Declare only the `rlib`.** `[lib] crate-type = ["rlib"]` in `rust/Cargo.toml`. A shared library listed there is built for every crates.io consumer too, and breaks the `no_std` ones (ledger: "A cdylib in the manifest breaks `no_std` consumers"). The shared library is built by naming its crate type on the command line instead.
2. **The `cargo cdylib` alias** in `rust/.cargo/config.toml`, which the forge calls for the native core on every leg and which is the dev loop's build command:

   ```toml
   cdylib = ["rustc", "--release", "--crate-type", "cdylib", "--no-default-features", "--features", "cdylib", "--config", 'profile.release.panic="abort"']
   ```

   The output stays in `target/release/`, where every binding's dev-loop fallback probes. **The forge requires this alias** in any crate that calls `hyper-build-native.yml`; a crate without it fails at the build step with `no such command: cdylib`.
3. **Features.** `default = ["std"]`, so a crates.io consumer, the test harness and the benchmarks get `std` as normal; `#![cfg_attr(not(feature = "std"), no_std)]` in `lib.rs`; `staticlib = []`, the panic handler for the `no_std` artifacts; and `cdylib = ["staticlib"]`, which adds what a `no_std` *shared* library needs on top (items 5 and 6). The extension features (`python`, `ruby`, `php`) name `std` themselves.
4. **Panics abort, for that one build only.** A `no_std` artifact cannot unwind; rustc refuses to build it otherwise. The alias sets `panic = "abort"` with `--config` instead of in `[profile.release]`, because a profile setting would reach the Python and Ruby extensions too, where PyO3 and Magnus can turn a Rust panic into a host exception only if it unwinds. At a C ABI boundary a panic was always a process abort anyway; under `no_std` it is the same abort, without the message printed first.
5. **A hidden `rust_eh_personality`.** `core` ships precompiled with unwind tables, and one that survives into the library can name the personality routine (in HyperCast, the 128-bit division helper's does). A static library leaves that reference for the final link; a shared library *is* the final link, so without a definition every `dlopen` fails with `undefined symbol: rust_eh_personality`. Nothing calls it under `panic = "abort"`, so a bare `ret` is enough. It is written in `global_asm!` with `.hidden` (ELF) / `.private_extern` (Mach-O) visibility rather than as a `#[no_mangle]` function, because a `#[no_mangle]` item is exported from a shared library whatever its Rust visibility. It is compiled only under the `cdylib` feature: two Hyper* static libraries that each defined it could not be linked into one program — the same collision that keeps `std` out of the static libraries (ledger: "Linking the core, where a binding can"). Windows needs none (its unwind tables name the C runtime's handler) and neither does wasm32. Include it even if nothing references it yet — HyperUuid's is dropped by the linker today — so the first change that does pull a reference in still produces a library that loads.
6. **An explicit C runtime link.** With `std`, the C library comes in through `std`'s own link directives. Without it nothing names it: on Linux the library links with no `NEEDED` entry at all, its imports unversioned and resolved only because the host process happens to have libc loaded (and the forge's musl check rejects it), and on Windows nothing names where `memcpy`, `__CxxFrameHandler3` and the DLL entry point come from. `#[link(name = "c")]` on Unix, and on MSVC `msvcrt` (or `libcmt` under `crt-static`) — the same choice `std` makes through the `libc` crate, so the library depends on exactly what the `std` build did.
7. **The wasm32-wasip1 module keeps `std`**, under its own `cargo wasm-module` alias (the forge's wasm steps spell the same build out). Its hosts allocate their buffers through the module's exported `malloc`/`free`, which come from wasi-libc by way of `std`'s allocator, and a `no_std` module does not link wasi-libc at all (`undefined symbol: memcmp`). It is also small already: 137 KB for HyperCast, 49 KB for HyperUuid.
8. **Prove the exports cannot panic** with dtolnay's [`no-panic`](https://docs.rs/no-panic) behind a `no-panic` feature, every PR. Its build must keep `std` and unwinding: `no-panic` detects a panic path by the unwind edge it leaves, and under `panic = "abort"` there is none, so the check would pass whatever the code did. (Plant a panic in an export once to see it fail.)
9. **Profile:** `[profile.release]` with `lto = true`, `codegen-units = 1` and `strip = true` (ledger: "A cdylib in the manifest breaks `no_std` consumers" has why LTO only reaches a cdylib built on its own), `[profile.bench]` with `strip = false` so a profiler keeps its symbols, and `[profile.staticlib]` inheriting release with `panic = "abort"` for the static libraries. Stripping drops only the symbol table — the machine code is byte-identical, measured on HyperUuid's linux-x64 library (19,448 → 16,632 bytes, the same `.text` hash), and the 13 exports keep their names in the export table — while the archives keep their symbols, since a static library is not linked and its consumer's linker resolves the core through them. It costs internal function names in a native crash dump, which with fat LTO inlining nearly everything into the exports is little; the tagged source rebuilds unstripped if one is ever needed.
10. **CI in the crate's own repo**, beside the forge jobs:
    - `check-cdylib` — builds `cargo cdylib` on all seven native RIDs, asserts the export list is the C ABI symbols and nothing else (Linux and macOS, where `nm` can list it), asserts the musl builds depend on musl's libc alone, and loads that exact library through Python's ctypes and calls every export, so it is `dlopen`ed and called the way a host does. The per-platform pieces in items 5 and 6 are only ever proven by loading the result.
    - `check-no-std` — `cargo check --no-default-features` for a bare-metal target, plus a real `default-features = false` consumer on the host and `wasm32-unknown-unknown`.
    - `check-no-panic` — item 8.
    - `cargo fmt --check` and `cargo clippy -- -D warnings`, over each configuration that compiles different code (default with tests, `no_std` bare metal, `no_std` cdylib, each extension that builds without its interpreter's headers, the fuzz target).
    - `check-msrv` — `cargo check` of the library and the `no_std` cdylib on exactly the `rust-version` the manifest declares, read from the manifest. Declare the lowest that builds (1.85 is edition 2024's own floor); the tests may use newer APIs.
    - `check-semver` — [`cargo-semver-checks`](https://github.com/obi1kenobi/cargo-semver-checks) against the latest crates.io release, default features only. Since the version bump rides in the PR that makes the change, a breaking change under a non-breaking version fails the PR that introduces it.
11. **`rust/rustfmt.toml`** with `use_small_heuristics = "Max"`, committed before the first line of code. rustfmt's defaults break struct literals and short `if`/`else` expressions onto several lines well short of the 100-column limit; this keeps anything that fits on one line on one line. HyperCast went unformatted until its 0.5 work, and the default settings would have rewritten 1,376 lines where this one rewrote 266.

12. **Round-trip tests for every text form the core parses**: each value formats to the canonical form and parses back to itself, and every one-character edit of a valid string (replace, remove, insert, multi-byte UTF-8 included) parses exactly when a deliberately naive reference parser in the test says so, to the same bytes. `no-panic` proves a parser cannot crash; only this proves it reads the right bytes. HyperUuid's `tests/round_trip.rs`.

### Levers deliberately not pulled

What is left after the recipe trades something away. Revisit when the trade changes.

| Lever | Would gain | Why not yet |
| --- | --- | --- |
| `panic_immediate_abort` (an immediate-abort panic strategy that rebuilds `core` without its panic formatting) | The last of `core`'s panic formatting; small, unmeasured | Nightly Rust only. **Adopt when it reaches stable.** |
| [Miri](https://github.com/rust-lang/miri) over the unit tests, every PR | Undefined behaviour in the `unsafe` pointer handling at the C ABI (out-of-bounds, misalignment, aliasing), the one class of bug `no-panic` and the suites cannot see | A nightly-only tool, and not headed for stable, so this waits on a decision, not on Rust: adopting it means one CI job on a pinned nightly date, bumped deliberately, with its tests trimmed for an interpreter roughly 50–100× slower than native. |
| Java: link the static archive into a GraalVM Native Image, as C# Native AOT does | No library extracted and loaded at startup: one executable, like the C# and Go builds | **Proven feasible on linux-x64 (GraalVM CE 25.4, October 2026), parked because the only way in is GraalVM's internal API.** Native Image's public `Feature` API cannot add linker options, so the jar would carry a Feature that casts to the builder's `FeatureImpl.BeforeImageWriteAccessImpl` and registers a linker-invocation transformer (the hook GraalVM's own `JNILibraryLoadFeature` uses), needing `--add-exports` for `com.oracle.svm.hosted` and `com.oracle.svm.core`. The image also hides every symbol but its own behind an anonymous version script, so the exports need the experimental `-H:ExportedSymbolsVersion=SVM` plus a second version script naming them, and `--whole-archive` so `--gc-sections` keeps them; the binding then finds them with `SymbolLookup.loaderLookup()` under Native Image (`defaultLookup()` searches only libc). `native-image.properties` alone cannot do it: `${.}` is not a file path inside a jar, and the properties cannot vary by OS or architecture. macOS (`-force_load` and exported-symbol lists) and Windows (`/WHOLEARCHIVE` and `/EXPORT`, with `loaderLookup` over an `.exe` unconfirmed) would each need their own linker handling, and a fully static musl image likely cannot look symbols up at all. So it is fragile — any GraalVM release can break the internal API, which every repo would then need a native-image CI job to notice — it is three per-OS code paths against a goal of fewer, and it buys little: Native Image already works from the same jar by extracting the shared library at startup. **Adopt when GraalVM offers a public way to add linker options and export symbols from a Feature.** |
| Java in the browser, as C# (Blazor), Rust, Python (Pyodide), Go (TinyGo) and Ruby (ruby.wasm) have it | The JVM binding running inside a web page | **Parked until GraalVM's Web Image (`--tool:svm-wasm`) is mature and can call or link native code.** Every other browser route works because that language's wasm toolchain links a native archive into its output (Emscripten, LLVM's wasm-ld, a static interpreter build); no Java-to-wasm compiler can. Web Image is experimental and has no FFM, TeaVM has no native code at all, and CheerpJ runs a JVM whose native methods can only be JavaScript. The one workable route — load the core as a wasm module of its own and call it through Web Image's `@JS` interop, copying 16 bytes a call — is a second binding with its own glue, not the existing one running in a browser, and nothing has asked for it (October 2026). |
| PHP in the browser through WordPress Playground's `@php-wasm`, as C#, Rust, Python, Go and Ruby have it | The PHP binding running inside a web page | **Proven (October 2026), not shipped: waiting on demand, because of its size.** Unlike Ruby it needs no custom interpreter on the route that matters: the binding's `ext-php-rs` extension, built as a static library for `wasm32-unknown-emscripten` and wrapped as a side module by Playground's `@php-wasm/compile-extension`, loads into the stock `@php-wasm/node` and `@php-wasm/web` runtimes (PHP 8.5, JSPI) and runs in node and headless Chrome. What it costs: a 128 KB module per supported PHP minor, each matched to its PHP exactly, built per minor in CI from a ~4 GB Playground image, plus a distribution channel to choose for a binding whose Composer package is FFI only. Two upstream issues it found, neither blocking with the flags the recipe passes: ext-php-rs does not compile against a 32-bit `zend_long` ([extphprs/ext-php-rs#800](https://github.com/extphprs/ext-php-rs/issues/800); Playground's PHP is 64-bit), and `compile-extension` drops four flags for cc-rs's C code, so the module fails to load with `bad export type for '__THREW__'` ([WordPress/wordpress-playground#4377](https://github.com/WordPress/wordpress-playground/issues/4377)). The full recipe is in HyperUuid's `php/README.md` (WebAssembly). A ~90-line C extension over the `no_std` emscripten archive also worked, at 12 KB a module and on 32-bit PHP, but is a second native implementation in C. |
| `opt-level = "s"` or `"z"` | Likely tens of KB | Likely slower calls, and speed is what the libraries are for. Unmeasured; benchmark before considering. |
| HyperCast: one shared integer engine instead of eight monomorphized copies | Perhaps 20–30 KB (the eight integer doors are about 4.5 KB each) | Housekeeping worth doing, but each door is its own hot path; needs A/B benchmarks first. Unmeasured. |
| PGO, `-C target-cpu` | Some speed | Build complexity, or binaries that will not run on older CPUs of a RID. |

## The ledger

Build archaeology, each item paid for once in a real red run (also commented at the workflow step that pays it):

| Lesson | Detail |
| --- | --- |
| Darwin extension linking | A Ruby/Python extension must **not** link the host runtime — `rb_*`/`Py_*` symbols resolve from the host process at load, which needs `-Wl,-undefined,dynamic_lookup`. maturin/rake-compiler arrange this; a plain cargo invocation does not. Linux allows undefined symbols in shared libs by default, so this only ever fails on macOS. |
| Temurin × win-arm64 | Adoptium ships Windows ARM64 JDKs for **21 and 23 only** (no 25 or 27 assets, re-checked 2026-09). The pipeline pinned 23 for that reason until 23 itself reached end of life; it now runs JDK 25, on Temurin for five legs and Microsoft's build of OpenJDK on win-arm64, which does ship that platform. |
| musl: no cdylib by default | Every `*-linux-musl` Rust target defaults to a statically linked C runtime, and under that default rustc cannot emit a cdylib. Asked for one on the command line (`cargo rustc --crate-type cdylib`) cargo stops with "cannot produce cdylib ... the target does not support these crate types"; a manifest that lists the crate type only gets a "dropping unsupported crate type" warning, the rlib, and exit 0. `-C target-feature=-crt-static` is what produces the `.so`. Check for the file, not the exit code. |
| musl: libgcc_s | A dynamically linked musl build keeps a `NEEDED` entry for `libgcc_s.so.1` (Rust's unwinder), which the bare `alpine`, `python:*-alpine` and `golang:*-alpine` images do not ship; the library fails to load there. `-static-libgcc` does not help, because rustc names `gcc_s` explicitly. A directory on the link path in which `libgcc_s` is a linker script naming `libgcc_eh.a` and `libgcc.a` does, and leaves musl's libc as the only dependency. Both archives: on aarch64 the unwinder calls libgcc's outline-atomics helpers, and naming only `libgcc_eh.a` linked on x86_64 and failed on aarch64 with ``undefined reference to `__aarch64_swp8_acq_rel'``. |
| musl platform gems vs `*-linux` | With both `x86_64-linux` and `x86_64-linux-musl` published, Bundler (2.5, 2.6, 4.0) and RubyGems 4's `gem install` pick the musl gem on Alpine, but `gem install` on RubyGems 3.5/3.6 (what Ruby 3.3 and 3.4 ship) picks the glibc `x86_64-linux` one — even with `--platform x86_64-linux-musl` — because a version-less `linux` platform matches a musl Ruby. Measured on `ruby:3.3/3.4/4.0-alpine` in October 2026. Naming the glibc gems `x86_64-linux-gnu`/`aarch64-linux-gnu` instead (nokogiri's scheme) made every combination resolve correctly in the same test, glibc images included, so that is what the platform gems are called. |
| A cdylib in the manifest breaks `no_std` consumers | Cargo builds every crate type a dependency's `[lib]` lists, not just the one the consumer links. With `crate-type = ["cdylib", "rlib"]`, a `default-features = false` consumer therefore also built a no_std cdylib, which is a linked artifact with no panic handler: "`#[panic_handler]` function required, but not found", on the developer's own machine and on `wasm32-unknown-unknown`, for both crates, through 0.4.0. The bare-metal `cargo check` in CI stayed green the whole time because a target that cannot produce a cdylib drops the crate type. The manifest now declares only the rlib and every shared-library build names its crate type (`cargo rustc --release --crate-type cdylib`, `cargo cdylib` in each crate), the way the static libraries already did; each repo's `check-no-std` job builds a real consumer on the host and for the browser. Side effect, measured: cargo only passes `-C lto` for a cdylib built on its own, so the libraries came out 15–18% smaller at the same speed. |
| Build the package where a failure is cheap | The wheels were built in each `release.yml`, at the tag, because a wheel carries its version in its file name. Once the libraries embedded the version, the release already had to reuse a CI run built at the bump commit, so that reason was gone — and what remained was a packaging matrix whose first ever run happened after other registries had published. 0.4.0's osx-x64 wheel failed its first install (setup-python's "x64" macOS build is universal and ran its arm64 slice) with crates.io, NuGet, Maven Central and RubyGems already out. `hyper-build-wheels.yml` now builds, installs and attests the wheels on every CI run, and the release downloads, verifies and publishes them. |
| A library that reports its version | Once the core exports its own version, a native library is no longer version-agnostic, and "reuse the last green CI run's artifacts at tag time" quietly ships the previous version's number: HyperCast 0.3.0's NuGet package, jar, gems and committed Go/Swift/PHP libraries all report 0.2.0, with every run green, because they were built a minute before the bump. The bump commit needs its own CI run, staging has to follow it, and the tag goes on the staging commit; `release.yml` refuses a run or a committed library built at any other version. |
| A `no_std` shared library | Dropping `std` from the `cdylib` (see [The Rust core](#the-rust-core)) failed three ways before it worked. `dlopen`: `undefined symbol: rust_eh_personality`, named by an unwind table `core` precompiles in — a static library never sees it, because its reference is left to the final link. Exports: a `#[no_mangle]` stub fixed loading but became a 23rd export, since `#[no_mangle]` exports whatever the Rust visibility says; `global_asm!` with `.hidden`/`.private_extern` does not. Linkage: with no `std` nothing names the C library, so the Linux `.so` had no `NEEDED` entry at all and the forge's musl check would have rejected it. And `-C panic=abort` belongs on that one build, not in `[profile.release]`, or the Python and Ruby extensions abort where they used to raise. |
| rust-lld keeps `std` alive on linux-x64 | Since Rust 1.90 `x86_64-unknown-linux-gnu` links with rust-lld. lld keeps `std`'s personality routine live from `.eh_frame`, and through it the panic hook and backtrace symbolizer: HyperUuid's linux-x64 library was 346,840 bytes with lld and 30,080 with GNU ld, same code, while its arm64 build (system linker) was 74 KB. `-C link-arg=-Wl,--why-live=<symbol>` prints the chain; a `no_std` build has no such routine to keep. If a size moves on one platform only, compare linkers before code. |
| `no-panic` needs unwinding | dtolnay's `no-panic` turns a panic path into an undefined symbol by way of the unwind edge it leaves. Under `panic = "abort"` there is no edge, so the check passes no matter what the code does. Build the proof with `std` and unwinding, even though the shipped library aborts — and plant a panic once to see it fail. |
| A float parser the proof accepts | HyperCast's `cast_f32` and `cast_f64` were the only exports outside the no-panic proof: they handed their normalized text to `core`'s float parser, whose slice-index checks the optimizer cannot remove, and nothing short of not calling it changes that. The conversion is the crate's own now (`rust/src/float.rs`): Clinger's fast path and Eisel-Lemire, the two algorithms `core` itself runs, over a 128-bit powers-of-five table whose generator is recorded in the table's file, and, for the rare input those cannot settle, an exact integer division on fixed stack arrays in place of `core`'s digit-shifting slow path — slower, and simple enough to write without an index in it. Every path is held to `core`'s bits over about a million and a half generated strings, exact halfway points and 1,100-digit expansions among them, with the exact step also run alone. Measured against the 0.6.1 door on linux-x64: within 4% either way on five workloads, and 1.7 KB more library. Two things it taught. The first version was up to 43% slower for one reason, reading the digits twice; one pass, eight digits at a time, is what `core` does and what closed the gap. And the panic planted to prove the proof was live has to be one the optimizer cannot discharge: indexing the table with an exponent that was already range-checked compiled to no check at all, and the proof passed with the plant in place, where an `assert!` on the parsed value failed it and named both doors. |
| PHP × win-arm64 | PHP has never shipped a native Windows ARM64 build — it runs under x64 emulation, which can never load an ARM64 native library. Skip the leg; win-x64 covers PHP-as-x64 for real. |
| Windows extension staging | A CPython extension module is a renamed DLL: `.pyd`. Ruby's `DLEXT`: `.so` on Linux, `.bundle` on macOS. |
| PyO3 on Windows | Needs no extra toolchain: the MSVC linker the core already builds with, plus CPython's import library inside the setup-python installation. Magnus on Windows is different — RubyInstaller rubies are MinGW-built, so a compatible extension is a `windows-gnu`-target exercise. |
| Composer proxies on Windows | `vendor/bin/phpunit` is a shebang script pwsh can't execute — invoke through `php`. |
| macOS runner Xcode | Ruby native-extension builds (mkmf) can fail if `xcode-select` isn't pointed at full Xcode — the pipeline sets it defensively. |
| Runner labels | `windows-11-arm` is GA, free for public repos. The Ubuntu legs name `ubuntu-26.04` and `ubuntu-26.04-arm` outright instead of `ubuntu-latest`, so both architectures build on one release and moving to the next is a commit rather than a label rollout that lands over several weeks. |
| Retiring a slow leg without retiring the platform | `macos-26-intel` took 37 minutes on HyperCast run 36894631512 against 8 for Apple silicon and 15 for the slowest Windows leg, every step 4–8x slower, on hardware Apple stopped selling in 2023 and a runner class GitHub retires by Fall 2027. The RID stayed and the leg went: Rust cross-compiles `x86_64-apple-darwin` on an arm64 Mac with only the target added, and `cargo test --target x86_64-apple-darwin` there runs the x86_64 test binary through Rosetta 2, so the core is still built, attested and genuinely tested. What a cross-build cannot give is anything compiled against a host runtime: a Magnus extension needs an x86_64 Ruby to build against, so that one piece moved to a small Ruby-only job on the Intel runner (`build-magnus-osx-x64`) — Rosetta on the arm64 image would need an x86_64 Ruby that setup-ruby does not install there. An `abi3` wheel needs no target interpreter to build, and `setup-python` with `architecture: x64` supplies one to smoke-test it. |
| A new Ubuntu image | Moving 24.04 to 26.04 changed four things, none of them in the Rust. Swift: no toolchain before 6.4 is published for 26.04. SwiftLint: its dynamically linked Linux binary needs `libxml2.so.2`, which 26.04 replaced with `libxml2.so.16`; the `swiftlint-static` binary in the same download needs nothing, and no Swift toolchain either. glibc: the image's is 2.43, but the libraries built on it still reference nothing past `GLIBC_2.34`, same as on 24.04, and `hyper-build-native.yml` fails the leg if that ever moves. bindgen: setup-swift puts Swift's own `clang` first on `PATH`, and bindgen asks that `clang` for the compiler headers while loading the newest system libclang, so 26.04's libclang 22 was parsing Swift 6.4's clang 21 headers and the ext-php-rs build failed on x64 in `xmmintrin.h` (arm64 has no such header and passed). The Linux legs now set `CLANG_PATH` and `LIBCLANG_PATH` to one system LLVM. |
| Swift 6.4's build system | Swift Build, SwiftPM's default from 6.4, stages a target's resources in `{Package}_{Target}.bundle` on every platform where the build system before it wrote `.resources` off macOS — which broke a binding that opened its native library out of that directory by name, and was one reason Swift stopped loading anything. It also links a binary target's archive by path where the old one copies it beside the products and passes `-l`, so the win-x64 leg runs the suite a second time with `--build-system native`. On 6.3, where Swift Build is opt-in, it dropped a binary target's module map when the package was reached through a product ([swift-build#1295](https://github.com/swiftlang/swift-build/pull/1295), fixed in 6.4): the package's own `swift test` passes, only a consumer fails, which is why `test-swift-static` builds the smoke executable on glibc on the current Swift too. |
| A toolchain setup action outlives its step | Whatever `setup-swift` puts in the job environment is still there for every later binding. Two failures, same cause, on the first Swift 6.4 run: on Linux its `clang` came first on `PATH` and bindgen mixed its headers with the system libclang (see the row above); on macOS, where the image's Xcode had no Swift 6.4, it installed swift.org's toolchain, exported `TOOLCHAINS`, and put that toolchain's bin directory ahead of `/usr/bin`, so a bare `clang` was swift.org's binary run directly rather than Apple's shim, with nothing to tell it where the SDK is. Ruby is configured with `CC=clang`, and its mkmf refused to build `fiddle` ("The compiler failed to generate an executable file"). Resetting `TOOLCHAINS` alone did not fix it, and a probe that linked with `cc` passed while mkmf kept failing: probe with the name the tool uses. A step cannot remove a `PATH` entry, so once the Swift steps are done the job prepends a directory holding only `clang` and `clang++` links to Apple's shims. |
| Linking the core, where a binding can | Three bindings link a static library instead of loading a shared one. Swift: SwiftPM links a per-triple archive declared as a binary target (SE-0482, Swift 6.2) on every platform — the only way to reach its static Linux SDK (musl) and its WebAssembly SDK, neither of which has a dynamic loader, and everywhere else it removes the resource directory a consumer had to deploy; the WebAssembly build is a plain wasip1 command, so it runs in a browser through a WASI shim too. Go: the archive goes on the cgo link line on Linux, macOS and Windows, and that is Go's only backend — nothing is embedded or extracted, a binary runs from a read-only filesystem, and a build without cgo is a compile error; on Windows it links the same MSVC archive as C#, which MinGW's linker reads, so there is one Windows archive per architecture. C#: `DirectPInvoke` plus `NativeLibrary` in the package's targets file hands the archive to the Native AOT linker, so a publish is one executable. What made it practical: (1) the archive rustc writes is 3–5 MB of core and compiler_builtins, but with fat LTO the crate's own object already holds everything it uses, so that one object re-archived is 10–210 KB; (2) it must be no_std with `panic = "abort"`, or two Hyper* archives collide on `rust_eh_personality` exactly as they did in Blazor; (3) MSVC has no 128-bit helpers, so the Windows archives keep the members a linker would pull, but that closure must not be used elsewhere — off Windows those helper objects carry unwind tables naming `rust_eh_personality`, which reintroduces (2); (4) cgo has no build constraint for the C library, so Go takes one Linux archive per architecture, the musl build, on glibc and musl alike; (5) SwiftPM and Swift Build match a variant's triple on vendor too, so the bundle spells Windows `x86_64-unknown-windows-msvc` (Rust's `pc` matches nothing) with MSVC's `{crate}.lib` name, macOS `arm64-apple-macosx`, and its info.json lists only the archives present, so a leg that builds one triple never names a missing one; (6) the static Linux SDK ships no XCTest, so musl is proven by a smoke executable, and 6.2's XCTest traps under WASI before any test runs, so the floor's WebAssembly check is the smoke executable too; (7) every one of the nine targets cross-compiles from one Linux runner, because nothing is linked. |
| Two Rust extensions in one ruby.wasm | ruby.wasm links every gem's extension into one interpreter, so the Magnus extension ships as a `wasm32-wasip1` static archive (the `{crate}-wasm` gem) and meets other Rust code at link time. The release-LTO object exports, besides `Init_*` and the C ABI, three symbols every std-carrying Rust extension defines identically: `rust_eh_personality` (which ruby.wasm's own wasi-vfs, a Rust staticlib, also defines), rb-sys's `ruby_abi_version`, and std's `EMPTY_PANIC`. HyperUuid alone stops on the first; HyperUuid with HyperCast stops on the other two. wasm `llvm-objcopy` can neither localize nor rename a symbol, so each gem's `extconf.rb` rewrites the three names in place to crate-owned ones of the same length (keeping every offset, and `EMPTY_PANIC`'s v0 mangling, valid) and then fails, by name, if the object still exports any other Rust-runtime symbol. The other ~575 shared names are identical `compiler_builtins` archive members, which wasm-ld pulls lazily and never duplicates. The first 32-bit build also caught HyperCast caching raw `VALUE`s as `u64`, which no 64-bit leg could. Two rbwasm traps: it runs `make clean` before `make static`, so the extconf leaves its archive under a name that is not `*.a`; and without `--remake` it returns the interpreter in `rubies/` whenever one exists under a name that hashes only the gem names, so a second build with the same gems (CI's prebuilt pass after its source pass, or any cache hit) links nothing new. CI passes `--remake` to every build, which rebuilds every extension and relinks Ruby. Magnus itself needed [#186](https://github.com/matsadler/magnus/issues/186) and [#187](https://github.com/matsadler/magnus/issues/187), fixed in 0.8.3 and 0.9.2. |
| FFM under GraalVM Native Image | A `static final MethodHandle` is only a constant to Native Image if its class is initialized when the image is built. Both Java bindings bound each downcall handle to its symbol's address, which exists only once the library is loaded, so the class initialized at run time and every call went through the image's method-handle interpreter: 6.4 µs for a call the JVM makes in 36 ns, and slower than the wasm backend in the same binary. The smoke test passed throughout — it proves the calls work, not what they cost. The shape that works: one address-less handle per C signature (`Linker.downcallHandle(descriptor, options)`), in a holder class that touches nothing but the linker, initialized at build time by a `native-image.properties` the jar ships; the address, looked up at run time, is the first argument. The same goes for any derived `ValueLayout` (it is read through a `VarHandle`). After: ~80 ns. JMH cannot run in an image, so the receipt is a hand loop built with the jar's own metadata, checked against JMH on the JVM first. |
| Swift on Darwin | Presenting Swift's `Duration` requires a `platforms: [.macOS(.v13)]` floor in Package.swift — Linux has no availability gates, so this only surfaces on macOS legs. |
| Benchmarking | `XDEBUG_MODE=off` for PHP (a loaded Xdebug inflates uniformly ~14x and looks plausible). Never run benchmarks concurrently with builds or each other. Time-based benchmarks carry explicit-timestamp variants — a wall-clock read is priced by the OS (~1µs on an arm64 WSL2 box whose clock defeats the vDSO; tens of ns elsewhere), not by the binding — and for the same reason every table names its machine and runtime: moving the published tables from that box to an x64 one took HyperUuid's lead over the `uuid` crate from 13–16x to 2x and over `UUID.randomUUID()` from 11–17x to 2.4–4.5x, with no code changed. One unwarmed call per fresh process times the library load, not the call (phpbench with `Revs(1)`: 0.8 ms reported for a 76 µs batch). pyperf's workers drop the environment unless `--inherit-environ` names the variable, so a backend switch silently measures the default backend. GraalWasm's JIT engages only when its artifacts are the same release as the GraalVM JDK; a mismatch runs the interpreter with no error, 17x slower. An interpreter built without its optimization flags (a default `pyenv install`) is 10–35% slower on both sides of a comparison — measure on the build people actually run. |
| Trusted Publishing bootstrap | A crates.io Trusted Publisher configuration **can only be created after the crate already exists** — [RFC 3691](https://rust-lang.github.io/rfcs/3691-trusted-publishing-cratesio.html): *"A Trusted Publisher Configuration can only be created after an initial manual publishing of a crate."* There is no equivalent of PyPI's **pending publishers**, which do let you pre-register a project that has never been published. So a brand-new crate is a two-step bootstrap: publish an empty placeholder once by hand with an API token ([`crate-placeholder/reserve-crate.sh`](crate-placeholder/) publishes and yanks it as `0.0.1` under the crate's name), register the trusted publisher on the crate's settings page, then every release, the first real one included, is tokenless. PyPI and RubyGems both have pending publishers, so crates.io is the only registry that needs this. Budget for it when standing up a new Hyper\* repo — it is the one publishing step that cannot be automated from an empty registry. |
| Attest before the irreversible step | Order attestation *before* whatever cannot be undone. A crates.io publish is permanent — yank hides a version, never deletes it, and the number can never be reused — so `cargo package` → attest → `cargo publish` means an attestation failure costs a re-run instead of stranding a published, unsigned artifact. Safe because a `.crate` is byte-identical wherever it is produced from the same commit (the commit sha rides inside `.cargo_vcs_info.json`, so a *different* commit yields different bytes). NuGet is the deliberate exception: nuget.org injects a repository signature into the `.nupkg` during validation, so the published bytes genuinely differ from the packed ones and it needs two attestations, one either side. |
| Doc gates need a CI invocation | A compiler-enforced doc gate only enforces where CI actually runs it. C# (`CS1591` + `TreatWarningsAsErrors`) and Rust (`#![deny(missing_docs)]`) fire on every PR because `dotnet test` and the core's cargo build compile there. Java's `javadoc -Xwerror` fires only when the `javadoc` task runs — which for a long time was the Maven publish and nothing else, so undocumented members sailed through every PR and failed the *release*. Run `javadoc` alongside the Java suite, not as a separate lint job: like C#, it is enforced by compilation, so it belongs on the leg that already compiles. |
| Allocation-proof tests | One `#[test]` fn per counting-allocator binary — `cargo test` spawns a thread per test fn, and thread creation itself allocates. Entropy sources can take a rare re-init slow path; treat a single one-off allocation flake as suspect-the-environment before suspect-the-code. |
